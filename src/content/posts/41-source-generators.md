A reflection-based mapper or serializer discovers its work at runtime: it walks types, reads attributes, builds expression trees and compiles delegates the first time a request needs them. That cost lands on your startup path and your first-request latency, and it is invisible until production warms the process under load. Source generators move the same work to the compiler. The Roslyn analyser runs during `dotnet build`, sees your types through the compilation, and emits plain C# that is compiled alongside the rest of the assembly — no runtime scanning, no warm-up, and everything visible in the object browser.

## How an incremental generator works

The `IIncrementalGenerator` interface is the modern entry point. Instead of re-running over the whole compilation on every keystroke, you declare a pipeline of transforms starting from a syntax provider, filter to the nodes you care about, then transform each one into a small model. Roslyn caches each stage by value equality, so editing one file only re-executes the stages whose inputs changed. Emitting is the last step and always goes through `SourceText.From`.

```csharp
[Generator]
public sealed class MapperGenerator : IIncrementalGenerator
{
    public void Initialize(IncrementalGeneratorInitializationContext context)
    {
        var models = context.SyntaxProvider
            .ForAttributeWithMetadataName(
                "MyLib.MapAttribute",
                predicate: static (_, _) => true,
                transform: static (ctx, ct) => BuildModel(ctx))
            .Where(static m => m is not null);

        context.RegisterSourceOutput(models.Collect(), static (spc, items) =>
        {
            var src = RenderMappings(items!);
            spc.AddSource("Mapper.g.cs", SourceText.From(src, Encoding.UTF8));
        });
    }
}
```

`ForAttributeWithMetadataName` is the fast path: Roslyn indexes the attribute name and hands you a `GeneratorAttributeSyntaxContext` with the target symbol and the semantic model already resolved, so you are not crawling every syntax node by hand.

### Keep the model small and equatable

The transform stage should return a record or struct containing only primitives and strings. If it returns Roslyn symbols, equality comparison walks the whole compilation graph and the incremental cache stops paying off — a full rebuild on every edit.

## What generators cannot do

- They cannot change existing code, only add new files.
- They cannot see runtime configuration, connection strings or environment variables.
- They cannot resolve types that are themselves generated by another generator in a way that needs a second pass; ordering is handled, but circular dependencies between generators are not.
- They run in the compiler, so a bug that hangs the generator hangs your build.
- Debugging means attaching to `VBCSCompiler` or emitting the pipeline output to disk with `EmitCompilerGeneratedFiles`.

## The trade-off

Generated code is still code: it lands in the build output, appears in stack traces and has to be maintained. You trade runtime surprise for build-time complexity, and you make the source of truth a template string rather than a loop. The payback is real for serialization, mapping, logging and DI registration — anywhere you currently pay reflection on a hot or cold path. It is not worth it for a handful of types where a hand-written file would be clearer.
